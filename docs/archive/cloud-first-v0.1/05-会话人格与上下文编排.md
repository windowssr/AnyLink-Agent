# 会话、人格与上下文编排

> 历史方案：云端 Agent 架构，已于 2026-11-22 被边缘 Agent 架构替代。仅作历史参考，当前设计见 [产品文档](../../product/README.md)。
## 1. 一个人格，多条会话

人格定义助理的称呼、表达、互动偏好与表现风格；会话承载具体交流历史；长期记忆承载经过整理的跨会话信息。三者分开管理。

同一助理在两台设备可以同时打开一条会话，也可以分别使用不同会话。共享人格不等于把两条会话的逐字上下文混在一起。会话历史以 OpenClaw 为权威，产品保存 `conversation_id -> gateway_instance_id / agent_id / session_ref` 映射。

## 2. 人格配置

人格包含名字、称呼、语言、语气、幽默程度、回复长短、主动交流偏好、声音和形象绑定。每次发布产生 `persona_revision`；运行开始时捕获版本，不能在同一段话生成过程中突然切换。

情绪表达是可解释的交互状态，例如关心、轻松、专注和庆祝。不得把“看起来担心”当作系统检测出真实危险的证据，也不得让角色状态改变任务权限或编造任务成功。

用户说“以后简短一些”时，先判断这是当前会话要求还是长期偏好。只有语义足够明确，才保存长期偏好；用户可在记忆中心查看和更正。

## 3. 单次运行上下文

每个运行生成一个服务端 `context_snapshot`：

- 主人、助理、会话、请求、运行和受信来源身份。
- 人格版本、用户本轮意图、显式目标设备。
- 全局记忆 revision、相关事实引用、设备目录版本。
- 本次允许的工具与能力快照。
- 关联任务、可公开的步骤进度和当前限制。
- 模型路由、预算、检索截止时间和生成期限。

快照中的 ID 用于关联；实际访问和写入时仍要检查当前授权。不得把历史快照当成永久访问凭据。

## 4. 上下文组装顺序

1. 加入固定系统规则和已发布人格。
2. 加入当前会话的有效历史与摘要。
3. 加入与当前意图相关的全局事实。
4. 加入来源和目标设备的目录；按需要取详细记忆。
5. 加入关联任务状态与工具返回证据。
6. 控制总预算，去重、裁剪低相关背景，并标明缺失覆盖。

检索失败时保留已知的结构化关键事实；不能让本轮聊天无限等待后台记忆整理。初始记忆注入预算建议上限 2,000～4,000 tokens，作为可调设计参数，不宣称这在所有模型上最优。

## 5. 工具和模型路由

默认聊天与常规工具规划使用服务器上的 DeepSeek provider。具体模型标识在部署时读取并验证，不把会变动的型号写死在产品协议中。

模型路由按文本、视觉、复杂规划、语音等能力选择。电脑 GUI 操作需要能处理当前截图格式的模型；通过独立配置选择，不能只因为文本工具调用正常就认定视觉能力可用。

任务规划需要长时间等待设备时，结束当前模型轮次，保存结构化任务。设备恢复后按当前上下文开启新的工作运行，不保留失效的临时工具权威。

## 6. 多端并发

同一会话的文本提交进入有序入口，第一版同一会话只允许一个前台生成运行。新消息可以排队，也可以通过显式“打断并继续”终止旧生成；不让两个运行无序写入同一段 assistant 文本。

不同会话可以并发，但共享事实修改走记忆服务的版本控制。设备上下文绑定 `run_id`，不能用一份“当前会话最后来源设备”缓存服务所有并发运行。

后台任务通过自己的任务上下文续跑。后台结果可以投递到发起会话，但不能假冒当前用户输入，或把任务日志无选择地变成长时记忆。

## 7. 响应所有者

每轮响应只有一个 `response_owner`：文字 agent 或实时语音适配器。文字路径可以转 TTS；实时语音路径需经过统一工具与记忆接口。禁止两个模型同时生成独立答案，再随意拼接文字与声音。

最终文本、音频、字幕、动作都关联同一 `response_id` 和 generation。用户打断后，迟到事件不能复活旧播放。

## 8. 输出与记忆的关系

“回复已完成”只代表交流响应完成；它可以触发异步记忆候选提取，但不是外部任务的成功信号。任务结果必须来自任务账本；模型生成“记住了”之前，明确写入请求应已由记忆服务持久接受。

## 9. 验收

同一人格跨端一致；同会话消息有序；不同会话不串设备；人物风格变更按版本生效；检索超时能够降级；任务等待不占用悬挂模型循环；文字 / 音频 / 形象保持同一响应归属。
