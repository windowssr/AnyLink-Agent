# 数据模型与存储

> 历史方案：云端 Agent 架构，已于 2026-11-22 被边缘 Agent 架构替代。仅作历史参考，当前设计见 [产品文档](../../product/README.md)。
## 1. 存储分工

产品 PostgreSQL 保存身份、逻辑设备、记忆、任务、授权、事件与通知。OpenClaw 自己保存会话与运行数据；产品经适配器访问，不直接更改 Gateway 内部数据库。

对象存储保存大附件和结果证据。设备本地数据库保存步骤回执与同步缓存。向量与摘要是可重建索引，不是权威事实。Redis 如引入，只承担临时缓存 / 扇出等职责。

## 2. 公共字段和约束

产品实体默认使用不透明 ID，包含 `owner_id`、`created_at`、`updated_at` 和 revision。时间保存 UTC；用户本地计划额外保存时区。外键与查询必须共同约束 owner，不能只靠难猜的 ID 保证归属。

同一事务修改领域实体和 outbox。跨数据库或跨进程不假装存在分布式原子事务；用受控状态、幂等、对账和补偿处理。

## 3. 核心表

### 身份和设备

| 表 | 关键字段 | 主要约束 |
| --- | --- | --- |
| `owners` | id、timezone、preferences_revision | 第一版单主人；扩展前重新评估隔离 |
| `auth_sessions` | binding、token_family、expires_at、revoked_at | 续期轮换，绑定撤销使会话失效 |
| `pairing_requests` | public_key_ref、nonce_hash、expires_at、approved_by、consumed_at | 单次消费；产品与节点配对分别记录进度 |
| `assistants` | owner、persona_revision、voice_profile、avatar_profile | 主人格配置版本化 |
| `logical_devices` | owner、label、platform、status | 名称不唯一，ID 才是身份 |
| `device_bindings` | logical_device、public_key_ref、node_id、binding_epoch、revoked_at | node 与安装绑定显式映射；撤销可查 |
| `device_capabilities` | binding、name、version、granted、ready、observed_at、revision | 能力版本与就绪时间独立保存 |
| `conversation_links` | owner、assistant、gateway、agent、session_ref | 与 Gateway 会话唯一映射；不存另一份可编辑历史 |
| `request_submissions` | request_id、payload_hash、session、gateway_run_ref、state | owner + request_id 唯一；未知提交不直接重发 |

### 记忆

| 表 | 关键字段 | 主要约束 |
| --- | --- | --- |
| `memory_items` | assistant、kind、scope、applicable_device、current_revision、status | global 的设备为空；device 的设备必填 |
| `memory_revisions` | item、revision、content、structured_value、valid_from/to、reason | item + revision 唯一；版本不可变 |
| `memory_sources` | revision、source_type、source_ref、source_device、event_time | 引用可追溯；权限不由 source_ref 自动授予 |
| `memory_index_entries` | item、indexed_revision、embedding_model、content_hash | 检索后回读当前 active revision |
| `device_memory_directory` | device、summary、source_watermark、dirty_since | 派生投影；不能覆盖事实 |
| `deletion_tombstones` | subject_type、subject_id、delete_revision、effective_at | 恢复与派生清理都检查墓碑 |

全局 / 设备的唯一事实约束不能仅用包含 nullable device 的普通唯一键，因为 NULL 的处理容易留下重复。实施时按 scope 建部分唯一索引，或使用经验证的规范化作用域键。语义相似仍需业务去重，不由数据库唯一键代替。

### 任务和授权

| 表 | 关键字段 | 主要约束 |
| --- | --- | --- |
| `tasks` | origin_device、target_device、conversation、status、plan_revision、deadline、result_ref | 状态与 07 保持一致；终态带结果原因 |
| `task_steps` | task、ordinal、operation、operation_hash、idempotency_key、status、dependencies | 同任务计划内步骤唯一；开始后操作不可变 |
| `step_attempts` | step、attempt、binding、lease_owner、lease_expiry、fencing_token、dispatch_state | 同一步骤不得存在两个合法活动认领 |
| `step_receipts` | step、attempt、receipt_id、operation_hash、binding_epoch、outcome、proof_ref | receipt ID 幂等；不接受跨 binding 冒用 |
| `execution_grants` | owner、device_binding、tool_scope、bounds、plan_hash、expires_at、revoked_at | 每次派发前核对当前版本与有效期 |
| `resource_leases` | device、resource_key、token、owner_attempt、expires_at | GUI 等互斥资源串行；未知动作先对账 |
| `task_projections` | task、workboard_card_ref、projected_revision、last_error | 看板可重建，不反向覆盖任务结果 |

### 事件、通知和媒体

| 表 | 关键字段 | 主要约束 |
| --- | --- | --- |
| `domain_events` | owner_stream_seq、event_id、aggregate_id、revision、type、payload | 同 owner 有序提交；可供客户端补读 |
| `outbox` | event_id、destination、status、attempt、next_attempt_at | 领域事务内创建，投递幂等 |
| `consumer_inbox` | consumer、event_id、result | 消费去重；处理和业务写入同事务 |
| `interactions` | trigger_key、reason、conversation、policy_revision、status | trigger key 去重 |
| `notifications` | interaction、device、dedupe_key、delivery_state、expires_at | provider 接受与用户打开分开 |
| `voice_sessions` | conversation、device、focus_lease、generation、memory_watermark | 焦点、generation 可撤销 |
| `assets` | owner、kind、object_key、hash、size、content_type、retention | 权限和生命周期由业务引用控制 |

## 4. 事件提交顺序

不能简单把普通数据库 sequence 的最大值当成“全部更早事务都已提交”的水位。第一版单主人场景可以在事务中锁定 owner 的 stream head，分配并写入 `owner_stream_seq`，确保相同 owner 的可见事件按提交顺序推进。

该串行点只处理需要恢复的领域事件，不承载每个文本 token 或音频帧。未来吞吐不足时替换事件分区方案，仍需保持游标不会漏掉迟提交事件的性质。

## 5. 附件

附件先创建 upload intent，上传完成校验大小、类型与 hash 后变为可引用。数据库保存 object key，不保存任意客户端本地路径。孤立上传定期清理；删除业务对象时按引用与保留策略回收。

截图、模型资产、执行证据和用户文件使用不同 retention policy。下载链接短期有效，不能让一个附件 URL 变成永久权限。

## 6. 本地回执数据库

设备至少保存 step identity、operation hash、accepted_at、started_at、finished_at、outcome、proof 和 server_ack。先写 accepted，再产生外部动作。终态回执上传成功且过保留窗口后才可清理。

系统重装导致本地日志丢失时，不推断历史动作没有发生。旧绑定的未知步骤仍需服务器和外部后置条件核验。

## 7. 数据生命周期

长期事实默认保留至更正 / 删除；候选与临时状态设置期限；音频默认不长期保存；事件、回执、日志和备份的期限分别配置。V0 不预先填造容量预算，先记录每天增长量，再确定实际保留窗口。

备份恢复必须考虑 Gateway 会话库、产品库和附件的一致恢复点。详见 [部署运维](17-部署运维与数据控制.md) 和 [故障处理](21-一致性与故障处理.md)。
