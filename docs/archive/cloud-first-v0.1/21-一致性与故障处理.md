# 一致性与故障处理

> 历史方案：云端 Agent 架构，已于 2026-11-22 被边缘 Agent 架构替代。仅作历史参考，当前设计见 [产品文档](../../product/README.md)。
## 1. 必须保持的不变量

1. 同一个事实只有一个当前权威 revision，派生索引不能改写它。
2. 同一幂等键不能对应两个不同操作内容。
3. 同一步骤没有两个合法活动执行者；未知旧动作先对账。
4. 任务成功需要执行证据，聊天完成不等于任务成功。
5. 所有权和执行授权以当前受信状态为准，历史来源不授予权限。
6. 用户打断后，旧 generation 不再播放或驱动口型。
7. 提醒、任务和明确保存的事实不能只存在于进程内存。
8. 恢复旧数据不会自动重放可能已经产生副作用的命令。

## 2. 事务边界

产品数据库内，将领域写入和 outbox 放同一事务。索引、通知、Gateway 调用、设备动作都在事务外完成，通过稳定 ID、状态和重试策略衔接。

消费 outbox 的 worker 记录投递 attempt；目标方使用 inbox 或等价去重。目标方已经处理但 ACK 丢失时，重传只能返回同一处理结果，不能再产生一次操作。

Gateway 如果缺少足够强的提交去重与查询，不能伪造这一保证，必须保留 submission_unknown 并阻止盲重发。

## 3. 故障矩阵

| 故障点 | 可能已经发生什么 | 恢复方式 | 禁止做什么 |
| --- | --- | --- | --- |
| API 接受前断线 | 请求可能未保存 | 同 request ID 查询 / 重试 | 换 ID 再发一次 |
| 产品已保存，Gateway ACK 丢失 | run 可能已启动 | 关联查询，必要时 submission_unknown | 直接启动第二个 run |
| 事实已提交，索引失败 | 新事实已生效 | outbox 重建，读取当前版本 | 用旧索引覆盖正文 |
| 删除已提交，缓存未失效 | 缓存仍有旧文本 | 当前状态过滤，停用过期语音快照 | 继续返回旧事实 |
| 步骤租约已拿，尚未派发 | 通常无外部动作 | 确认未接受后重新排队 | 假设所有租约过期都可重试 |
| 设备 accepted 后断线 | 可能未开始，也可能已完成 | 查本地回执和后置条件 | 当作普通网络失败重放 |
| 动作后、终态回执前崩溃 | 外部效果未知 | needs_reconciliation | 把本地日志缺失当未执行 |
| 云端提交结果后 ACK 丢失 | 已记账 | 设备重传同回执，幂等返回 | 增加另一条成功步骤 |
| 取消与派发并发 | 命令可能在途 | 阻止后续，核验当前步骤 | 立刻宣称完全取消 |
| 撤销绑定与回执并发 | 有旧动作证据 | 隔离迟到证据，当前流程核验 | 恢复旧执行权 |
| 语音焦点切换 | 旧音频仍在缓冲 | 本地停止，失效旧 generation | 等整段说完才切换 |
| 推送 provider 超时 | 可能已接受 | 同通知 ID 查询 / 重试与去重 | 立即全设备广播 |
| 服务器从旧备份恢复 | 快照后动作可能已发生 | 只读恢复、回执对账和控制记录应用 | 自动认领所有旧 running |

## 4. 索引一致性

每个索引条目携带 `indexed_revision`。返回检索命中前回读当前事实，删除 / 修订后旧命中即使仍在向量库，也不会直接返回给模型。摘要记录来源水位，落后时回查或跳过。

“索引更新成功”只更新投影状态，不触碰权威正文。重复或乱序索引事件以 revision 防止回退。清理失败有积压指标和重试，不阻塞正常事实提交。

## 5. 任务恢复扫描

扫描所有过期认领和未终结步骤，按最后可证实阶段处理。queued 可正常重新调度；leased 必须确认是否派发；accepted / running 优先查询设备；结果不确定进入 needs_reconciliation。

恢复扫描本身幂等，使用条件更新和当前 token。先前 worker 回来时不能覆盖新认领或当前结果。同一资源存在未知旧动作时，不允许新冲突任务抢占资源。

对账可以以设备可信回执、外部可核验记录或用户明确的人工确认结束。人工确认记录操作者、理由与证据类型，不能伪装成自动设备回执。

## 6. 跨库与投影

Gateway 历史、产品任务和 Workboard 投影之间没有跨库原子事务。关联映射使用版本和明确状态；投影失败允许重建，源数据不回退。

如果 Gateway 会话显示结束而设备任务仍运行，产品 UI 分开显示“回复结束”和“任务运行中”。看板卡片终态不能强制结束未对账的设备步骤。

## 7. 备份恢复中的旧权限

恢复旧库前停止所有派发。用最新可得的撤销记录核对设备、使用新部署代次、重新建立受限连接，并等待旧短期权威过期或明确失效。不能认为数据库中一条旧 grant 仍然有效。

恢复点之后存在但云端丢失的任务回执作为待核验孤立记录处理。保留证据、通知主人，不用另一条“相似任务”自动吸收这些结果。

如果控制记录或设备状态无法核实，维持只读 / 待对账，不在未知条件下自动恢复写操作。

## 8. 演练顺序

先用无副作用查询验证请求与事件恢复，再用临时目录文件操作验证步骤，最后在可控测试应用验证 GUI。逐个切断 API、worker、Gateway、设备 UI、设备执行器和网络。

每次演练记录注入位置、前置状态、实际外部结果、恢复后状态和是否产生重复。只看 UI 最终显示成功不足以通过验收。

## 9. 面向用户的处理入口

待对账任务应提供“查看已知结果”“重新检查”“确认已经完成”“确认未发生并重新执行”“保留暂停”等符合当前证据的动作。重新执行创建明确新 attempt / step，不覆盖未知历史。

操作入口不能要求用户理解 fencing token 或 outbox。用户只需要知道发生了什么、哪些已确认，以及再次执行可能影响什么。
