# 主动联系与通知

> 历史方案：云端 Agent 架构，已于 2026-11-22 被边缘 Agent 架构替代。仅作历史参考，当前设计见 [产品文档](../../product/README.md)。
## 1. 目标

让助理在有明确理由、合适时机和用户允许的节奏下主动出现。主动联系由云端统一决定，客户端只负责接收和呈现，避免每台设备各自发起一次关心。

## 2. 触发来源

| 来源 | 例子 | 默认策略 |
| --- | --- | --- |
| 用户明确要求 | 今晚提醒整理资料 | 按约定时间与重复规则触发 |
| 任务事件 | 任务完成、等用户处理 | 合并同一任务的重复事件，按重要程度触达 |
| 已授权目标跟进 | 周末看看研究计划进度 | 需要启用跟进偏好，能解释对应目标 |
| 轻量伴随交流 | 适度问候、继续先前话题 | 默认关闭或低频，用户可单独开启 |
| 设备状态事件 | 目标设备恢复后任务可继续 | 优先恢复任务，不为每次连接变化都打扰 |

模型可以建议一次互动，最终是否触发、何时触发和投递到哪台设备由策略决定。

## 3. 策略输入

策略读取触发事件、用户时区、免打扰、频率、近期互动、相关会话、设备 presence 与声音焦点。设备活跃是有限证据，不据此断言用户情绪或精确活动。

所有时间同时保存 UTC 实例和用户时区 / 本地规则。重复提醒保存 recurrence 与 timezone，时区变化和夏令时按明确规则重新计算，不能只存“每 24 小时”。

初始默认：任务结果可正常通知；非必要问候最多每日 1 次、最短间隔 6 小时，用户可调整。它们是设计默认值，不是已验证的最佳互动频率。

## 4. 设备选择

优先发起会话所在的活跃设备，其次用户指定的通知设备，再次在线且允许通知的设备。实际播报必须同时持有声音焦点，并满足未锁屏 / 用户允许的播放策略。

找不到合适设备时生成会话未读和可用推送，不让所有设备同时响。多个设备仍同步同一 interaction 状态，主触达选择只控制打扰方式。

## 5. 持久流程

1. 触发事件进入云端 inbox，按 trigger key 去重。
2. 策略计算是否触发、延期、合并或丢弃，保存原因。
3. 创建唯一 `interaction_id` 与内容；需要生成文字时使用主助理人格。
4. 同事务创建 notification outbox。
5. worker 投递到选定设备 / 推送 provider，保存各级结果。
6. 客户端按 notification ID 去重，回传接收、展示和打开状态。

Provider 接受不等于设备收到，设备收到不等于用户读过。状态不得混写。投递超时不自动改为对所有设备广播，先处理既有投递是否未知。

## 6. 去重和焦点

同一任务同一终态使用稳定 dedupe key。推送重试使用同一 notification ID；系统支持时更新原通知，不再生成另一条。客户端本地保留最近去重记录。

声音播报需要短租约；旧设备在失去租约、进入不允许播放的状态或断开焦点心跳后停止。租约不保证操作系统通知绝不重复展示，因此产品同时依赖稳定通知 ID 和本地去重。

## 7. 内容边界

消息提供可理解理由和下一步入口。锁屏默认简短，不把完整私人事实、屏幕内容和敏感任务结果直接放进推送载荷。用户可以关闭预览、静音某类互动或暂停全部非必要主动联系。

“主动聊天”只向主人自己的产品客户端发消息。给其他人发邮件或即时消息属于另一个外部写任务，需要具体工具与对应授权，不由主动交流策略自行扩大范围。

## 8. 调度实现

提醒、触发与投递意图持久化在产品数据库。可以复用 OpenClaw 适用的 automations 触发能力，但产品保留自己的 interaction 去重与投递状态。插件的进程内定时器不能替代可恢复提醒。

## 9. 验收

覆盖服务重启、重复触发、免打扰、跨午夜与时区变化、设备无网络、推送 ACK 丢失、多端同时在线和任务结果合并。用户必须能查到每次主动联系的原因，并且一处关闭后所有设备生效。
